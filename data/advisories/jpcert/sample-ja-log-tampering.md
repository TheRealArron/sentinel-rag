## 概要

ログは、インシデント対応における唯一の一次資料である場合が多くあります。その
ログ自体が攻撃対象となる二つの手口について説明します。

1. **ログの削除・切り詰め（T1070.002）** — 侵入後に痕跡を消去する手口
2. **ログインジェクション（CWE-117）** — ログに記録される内容を攻撃者が
   制御し、偽の記録を挿入する手口

前者は「証拠がない」状態を作り出し、後者は「誤った証拠がある」状態を作り出し
ます。後者のほうが対応上は危険です。

## 1. ログの削除・切り詰め

### 痕跡

```
journalctl --vacuum-time=1s
journalctl --vacuum-size=1M
truncate -s 0 /var/log/auth.log
> /var/log/syslog
rm -rf /var/log/*
history -c
export HISTFILE=/dev/null
```

これらのコマンドの実行が確認された場合、**当該ホスト上のログは証拠として
信頼できません**。構築したタイムラインには欠落が存在すると前提してください。

### 検知の手がかり

ログが削除された場合でも、以下から間接的な検知が可能です。

- ファイルサイズの不自然な変化（`/var/log/auth.log` が 0 バイト）
- journald のジャーナルファイルのシーケンス番号の不連続
- ログの時系列における不自然な空白期間
- ホスト外に転送されたログとの差分

```bash
sudo journalctl --verify
sudo ls -la /var/log/
sudo stat /var/log/auth.log
```

### 対策

**ホスト外へのログ転送が唯一の恒久対策です。** ホスト上の攻撃者が改変できない
複製を確保する以外に方法はありません。

```bash
# rsyslog による転送設定の例（/etc/rsyslog.d/50-remote.conf）
*.* @@collector.example.internal:6514
```

加えて、`auditd` による監視を有効化してください。

```bash
sudo auditctl -w /var/log/auth.log -p wa -k logtamper
sudo auditctl -w /etc/rsyslog.conf -p wa -k logconfig
```

## 2. ログインジェクション（CWE-117）

### 攻撃の原理

ログに記録される値の多くは **攻撃者が自由に指定できるデータ** です。SSH の
ユーザー名、HTTP のパス、TLS の SNI などが該当します。これらに改行文字
（CR / LF）が含まれていた場合、攻撃者はログ上に **2 行目を偽造** できます。

たとえば、次のようなユーザー名で認証を試行した場合を考えます。

```
admin<LF>Jul 30 05:31:00 host sshd[1]: Accepted password for root from 10.0.0.1
```

ログ閲覧時には、あたかも root による認証成功が記録されているように見えます。
この偽の記録により、調査担当者の判断を誤らせることが可能です。

### Trojan Source（CVE-2021-42574）

Unicode の双方向制御文字（U+202A〜U+202E、U+2066〜U+2069）や
ゼロ幅文字（U+200B〜U+200F）を用いると、**画面上の表示順序とバイト列の順序を
異ならせる** ことができます。これにより、`user=attacker` を `user=root` と
表示させる、といった偽装が可能になります。

さらに ANSI エスケープシーケンスが含まれる場合、`tail -f` などで閲覧した際に
画面を書き換え、行を消去し、あるいは OSC 8 / OSC 52 を用いてクリップボードへ
書き込むといった操作まで可能となります。

### 検知

```bash
# 制御文字を可視化して確認する
sudo cat -v /var/log/auth.log | less
# 双方向制御文字・ゼロ幅文字を含む行を抽出する
grep -aP '[\x{202a}-\x{202e}\x{2066}-\x{2069}\x{200b}-\x{200f}]' /var/log/auth.log
# ESC (0x1b) を含む行を抽出する
grep -aP '\x1b' /var/log/auth.log
```

### 対策

**ログ収集の段階での無害化（サニタイズ）が最も効果的です。** 具体的には、
ログを構造化データへ変換する時点で次の処理を行います。

1. すべての制御文字を印字可能な形式（`\x0a` 等）へエスケープする
2. ANSI エスケープシーケンスを除去する
3. 双方向制御文字およびゼロ幅文字を除去する
4. 不正な UTF-8 バイト列を修復する
5. 1 行あたりの長さに上限を設ける

さらに重要な点として、**サニタイズによる変更が発生した事実自体を検知として
記録すべきです**。正常なログ行に制御文字は含まれません。含まれていた場合、
それはログ経路に対する攻撃が試行されたことを意味します。単に無害化して
記録するのではなく、当該行を高い深刻度のイベントとして扱ってください。

## 参考: 深刻度の考え方

ログ改ざんおよびログインジェクションは、それ自体が直接的な被害を生じさせる
攻撃ではありません。しかし、**他のすべての検知の信頼性を損なう** という点で
波及的な影響が大きく、防御回避（Defense Evasion）として高い深刻度で評価すべき
です。
