Five bugs, and how each one was caught

A bilingual security-operations engine: a dependency-free Go log ingestor feeding a Python retrieval engine. These are the five defects that were hardest to find — and, more usefully, the mechanism that found each.

Only one of these five was found by reading code. The rest were found by running the system and refusing to accept output that looked reasonable.

That is the thread worth pulling. Each defect below is filed with the mechanism that exposed it, because in every case the mechanism was the scarce thing — the bug itself was obvious the moment anything was pointed at it.

01

The API that took orders from any website

Caught by Probing the running server with curl instead of reasoning about the threat model. The reasoning had already concluded it was fine.

Sentinel's dashboard exposes POST /api/response/block. It records a decision to firewall an address; a host-side responder running as root reads that record and calls ufw. The endpoint is unauthenticated by design, because it binds to localhost and "localhost only" felt like a boundary.

It is not a boundary. A browser running on that host is already inside it. Any page the operator visits in another tab can issue cross-origin POST requests to 127.0.0.1, and the browser will send them.

The exploit, before the fix200 OK
curl -X POST http://127.0.0.1:8000/api/response/block \
  -H 'Content-Type: text/plain' \
  -H 'Origin: https://evil.example' \
  --data '{"target":"192.0.2.66","score":99,"reason":"csrf"}'

HTTP 200 — decision recorded, responder will enforce it

An attacker who can get an operator to open a tab can make the security engine firewall arbitrary addresses. Point it at the operator's own gateway, or at the upstream resolver, and the tool becomes the outage.

The fix that would not have worked

The instinctive answer is a CORS allowlist. It does not help. CORS does not stop the request from being sent or the side effect from happening; it stops the attacker from reading the response. For a request whose entire purpose is the side effect, the attacker never needed to read anything. A CORS policy here buys exactly nothing and feels like it buys everything, which is worse than no policy at all.

What actually closes it

Two checks, and the first one is the load-bearing one. A browser can only send a cross-origin request without a preflight if it qualifies as a simple request — and a simple request cannot set Content-Type: application/json. Requiring that header forces a preflight, and the preflight is refused. The Origin check is defence in depth on top.

engine/sentinel/guard.py
def check(self, method, content_type, origin) -> tuple[bool, str]:
    if method.upper() not in {"POST", "PUT", "PATCH", "DELETE"}:
        return True, ""

    # No Origin means the caller is not a browser page, so not a CSRF vector.
    if origin and self._normalise(origin) not in self.allowed_origins:
        return False, f"cross-origin request from {origin!r} refused. ..."

    if self.require_json:
        base = (content_type or "").split(";")[0].strip().lower()
        if base != "application/json":
            # Forces a cross-origin preflight, which is never satisfied.
            return False, "mutating requests must send Content-Type: application/json"
    return True, ""

Generalises to

A control that stops you seeing the answer is not a control that stops the action. And a network boundary that a browser sits inside is not a boundary at all — it is a shared address space with a friendly name.

02

The blast radius that walked backwards through time

Caught by Looking at a correct-looking answer and asking why a TLS renewal binary was in an attacker's blast radius. The graph was right; the question was wrong.

Given a compromised entity, Sentinel answers "what else could they have reached?" by walking a typed graph of hosts, accounts, processes and files. The first version was a plain breadth-first search, and it reported that the attacker had reached /usr/bin/certbot.

They had not. The path was real: attacker → root → certbot. But the second edge was a cron job that ran last week. Graph reachability has no notion of a clock, so it happily walks an edge that only ever fired before the attacker existed.

This is not an edge case. High-degree shared nodes — root, the host itself — connect nearly everything to nearly everything, so an untimed traversal over-reports catastrophically on real data. The number stops meaning anything and the operator learns to ignore it.

The first fix was also wrong

The obvious repair is to refuse any edge whose activity predates the attacker's arrival, and to arrive at the edge's last occurrence. That over-constrains: it pushed arrival times artificially late and dropped a file the attacker genuinely had touched. Tightening a wrong answer in the right direction still leaves a wrong answer.

The correct traversal arrives at the earliest occurrence that is not before the attacker was present — and, critically, uses relaxation rather than first-visit-wins. A node's arrival time can improve when a second route reaches it sooner, and an earlier arrival unlocks onward edges that a later one forbids. Plain BFS freezes the first arrival it finds and silently truncates the radius.

engine/sentinel/graph.py
if respect_time and here and edge.last_seen:
    # Nothing this edge ever did happened after the attacker got
    # here, so it cannot be part of what they reached.
    if edge.last_seen < here:
        continue
    # Arrive at the edge's earliest occurrence that is not before
    # the attacker was present. last_seen would over-constrain
    # every onward hop.
    there = edge.first_seen if edge.first_seen >= here else here

improved = (known_hop is None
            or hop + 1 < known_hop
            or (known_arrival is not None and there < known_arrival))

One honest footnote: on the 25-event sample fixture the clock changes nothing (7 and 12 either way). That fixture is five minutes of intrusion with no history, so there is no "before" to walk into. The constraint only earns its keep once there is a past — which is exactly when it matters and exactly when a small test fixture will not show you.

Generalises to

Reachability on a graph whose edges have timestamps is not reachability. If shared high-degree nodes exist — and in security data they always do — an untimed traversal answers a question nobody asked.

03

The bilingual floor that guaranteed nothing

Caught by Writing a test that asserted the feature's actual promise — "a Japanese source appears" — at the smallest interesting k, rather than asserting the code path ran.

The retrieval engine indexes English and Japanese advisories together and promises a per-language floor: an English query must still surface the Japanese advisory that explains the attack. Without it, an English query against a mostly-English corpus returns English-only results essentially always, and the bilingual claim is decoration.

The floor was implemented, the code path executed, and the guarantee did not hold. Two independent bugs, each of which alone would have been enough.

Bug one: the sort undid the top-up

The pipeline topped up under-represented languages with extra candidates, then merged everything, sorted by score, and truncated to k. But the topped-up hits are by definition lower-scoring than the ones that crowded them out — that is why they needed topping up. A score-ordered cut removes precisely the results the floor just added. The feature paid the retrieval cost and then deleted its own output.

Bug two: the quota starved the second language

Reserved slots were allocated language-by-language: fill English's quota, then Japanese's. With a floor of 2 and k=2, English consumed both slots and Japanese got none — an English-only result set, which is the exact failure the floor exists to prevent. The mechanism was most broken precisely where it mattered most.

engine/sentinel/retriever.py
# Collapse the *whole* candidate pool, then select. Truncating the pool
# before selection would silently discard the language top-ups.
parents = self._collapse_to_parents(hits)
return self._select_with_language_floor(parents, k, languages)

# ...and allocate round-robin, not language-by-language. Filling English's
# whole quota first consumes every slot when k is small.
for _round in range(floor):
    for lang in languages:
        if len(selected) >= limit:
            break
        ...take the best unselected parent in this language...
Generalises to

A quota applied before a global sort is not a quota. And a guarantee should be tested at its boundary — k=2, one slot per language — not in the comfortable middle where any implementation looks correct.

04

The correlator that graded its own homework

Caught by Reading the cited evidence rather than the confidence score. The scores were high. The citations were the same event, restated.

Shadow Search is an unattended daily worker. It ranks the last 24 hours by statistical surprise against a learned baseline, then retrieves supporting intelligence for each anomaly from the corpus and writes it up.

The corpus contains two kinds of document: CVE and JPCERT advisories, and windows of log events. Nobody told the retriever which kind constituted evidence. So for an anomaly derived from log lines, the nearest neighbours were — inevitably — other log lines from the same host at the same time.

The output was well-formed and confident. "This activity is suspicious, and here is the supporting intelligence: this activity." The system was citing itself, and the similarity scores were high precisely because the match was circular. Worse, those self-citations crowded out the advisories that are the entire point of correlating against a corpus.

engine/sentinel/shadow.py
# Restricted to advisories on purpose. The index also holds log windows,
# and without this filter the "supporting intelligence" for an anomaly is
# other log lines from the same host — circular, and it crowds out the
# JPCERT/CVE documents that are the entire point of correlating.
retrieved = self.engine.search(
    self.query_for(anomaly), k=self.settings.shadow_k, doc_types=["advisory"]
)

The fix is one argument. The bug was invisible to every test that asserted retrieval returned k results with scores above a threshold — which it did, happily, forever.

Generalises to

Retrieval that can return the query's own source is not evidence. Any RAG system indexing both the thing being explained and the things that explain it needs that distinction enforced at the query, because similarity will never make it for you — it will do the opposite.

05

The one field that switched off detection

Caught by A committed golden fixture changing from 25 events to 23. Nothing errored. Two alerts simply stopped existing.

Sentinel imports Sigma rules — the industry-standard YAML detection format — by transpiling them into a predicate tree the Go ingestor evaluates. Sigma rules carry a level (informational … critical), which maps cleanly onto Sentinel's 0–100 score.

Sigma has no concept of an outcome. Sentinel does: every event is success, failure, or attempt, read off the log line by the built-in rules. So the transpiler derived an outcome from the rule's level and assigned it. Reasonable-looking, and wrong, because that assignment was unconditional — it overwrote a value that had been read from the actual log text with one that had been guessed from a YAML field.

Elsewhere in the pipeline, the stateful correlator keys brute-force detection on exactly that field:

ingestor/internal/correlate/correlate.go
isAuthFailure := ev.Outcome == "failure" &&
    (ev.Category == enrich.CatAuth || ev.Category == enrich.CatPrivilege)

So importing a well-formed, industry-standard brute-force rule silently disabled brute-force and post-compromise correlation. The per-line detections still fired. The two aggregate incidents — the ones that turn six failures and a success into "this host was compromised" — vanished without a warning.

How it surfacedmake sample
regenerated data/samples/events.sample.jsonl (23 events)

ingestor/internal/enrich/enrich.go
// Outcome is deliberately NOT overwritten when the pipeline already derived
// one. Sigma has no outcome concept, so the transpiler's value is a guess
// from the rule's level — whereas a built-in rule read success/failure off
// the log line itself.
if ev.Outcome == "" {
    ev.Outcome = rule.Outcome
}
Generalises to

Know which of your fields are load-bearing. A field that reads like metadata in one module can be a control input in another, and the coupling is invisible from either end. A fabricated value must never overwrite a derived one.

Coda

A sixth, found while writing this page

Verifying the claim in defect 01 for this write-up meant standing the server up and re-running the attack. It was correctly refused. Then the legitimate request was also refused:

Same-origin request from the dashboard itself403
curl -X POST http://127.0.0.1:8137/api/response/block \
  -H 'Content-Type: application/json' \
  -H 'Origin: http://127.0.0.1:8137'

HTTP 403 — cross-origin request from 'http://127.0.0.1:8137' refused

The allowlist was built from settings.api_port. The server had been started with --port 8137. On any non-default port the dashboard's own block button was refused by a control designed to stop other sites — the same control as defect 01, wrong in the opposite direction.

The existing tests could not have caught it. They exercised the policy object directly with a hard-coded port 8000, and the defect was in the wiring between the bound socket and the policy. The fix completes the allowlist at the only moment the real origin is known:

engine/sentinel/server.py
# Trust the address we actually bound, not the one in settings.
bound_host, bound_port = server.server_address[:2]
router.csrf.allowed_origins |= router.csrf.default_origins(
    str(bound_host), int(bound_port))

The tests that tested nothing

Two verification failures from this project are worth more than any of the defects above, because both produced confident green output while checking nothing.

  • CI was reported green while it was red. The check used gh run list --limit 1, which raced the push and returned the previous commit's run. The status was true, about the wrong commit. The fix is to match runs by commit SHA and poll until that specific run completes.
  • A test proving the zero-dependency YAML fallback worked was proving nothing. It blocked the import with a find_module meta-path hook — an API removed in Python 3.12, so the hook was silently ignored and PyYAML stayed available throughout. The fallback parser was in fact broken on all four sample rules. CI, which installs no dependencies at all, found it immediately. The replacement sets sys.modules["yaml"] = None, and a guard test asserts the block is real before the tests that depend on it run.
The actual lesson

A passing test is a claim about your test, not about your code — until you have watched it fail for the right reason. Every regression test in this project is now written by breaking the fix, confirming the test goes red, then restoring it.
